# 대화 안에서 읽고 보고 다음 작업으로 이어가는 설계

Paseo의 채팅을 참고할 이유는 본문, 작업 내역, 결과물, 작성창을 같은 문맥에서 다룬다는 데 있다. Workbench에도 Markdown·Mermaid·첨부 이미지·도구 이미지·실행 기록 접기가 이미 있다. 새 계획은 그 기능을 묶고, 일반 답변의 로컬 이미지와 원격 기기의 결과물까지 연결한다.

## 사용자에게 보일 차이를 정의한다

| 상황 | 제안하는 동작 | 보존할 것 |
|---|---|---|
| AI가 여러 도구를 쓰며 긴 답변 생성 | 답변은 본문으로, 도구 내역은 “파일 4개 수정·검색 2회” 같은 요약으로 표시 | 실패·승인 필요·진행 중 상태는 즉시 보임 |
| 사용자가 이미지를 붙여넣음 | 보내기 전 썸네일, 전송 후 같은 이미지 카드, 확대·파일 정보 | 실제로 모델에 전달됐는지 표시. 실패한 첨부를 조용히 빼지 않음 |
| AI가 `결과/그림.png`를 만듦 | 답변에서 이미지 확인, 확대, 원본·폴더·관련 문서 열기 | 메시지 당시 이미지와 최신 파일을 구분 |
| AI가 Word·HWPX·PDF를 만듦 | 결과 카드에서 형식·판·위치를 확인하고 해당 편집 탭 열기 | 기존 자동 편집 집중, 독립 문서 AI, 외부 이음오피스 열기 |
| 위쪽 답변을 읽는 중 새 출력 도착 | 읽던 줄 유지, 새 내용 표시, 선택한 경우 끝으로 이동 | 텍스트 선택·복사와 검색 대상 위치 |
| 작업 중 후속 지시 입력 | “지금 반영”, “다음에 보내기”, “현재 작업 중단”을 구분 | 공급자가 지원하는 개입 방식만 제공 |
| 휴대폰에서 사진·스크린샷 전송 | 대상 호스트에 업로드 완료 후 같은 메시지 ID로 접수 | 네트워크가 바뀌어도 중복 실행하거나 초안을 잃지 않음 |
| 긴 도구 출력·거대한 답변 | 접기·페이지 로드·별도 전체 보기로 화면 부하 제어 | 원문 저장과 Ctrl+K 검색은 생략하지 않음 |

## 이미지를 표시하는 네 경로를 합친다

1. 사용자 입력 이미지. 현재 `Attachments`의 붙여넣기·드롭·업로드 경로를 재사용한다.
2. 도구 결과 이미지. 현재 `tool-images`와 provider 이미지 이벤트를 재사용한다.
3. 답변 Markdown 안의 로컬 이미지. 서버가 workspace와 실제 경로를 확인해 첨부 참조로 변환한다. 원격 휴대폰의 `C:\...` 또는 `/home/...` 파일 읽기로 처리하지 않는다.
4. 파일·문서 결과. 이미지는 대화에 표시하고, 복잡한 문서는 카드에서 기존 편집 탭으로 연결한다. 모든 MIME을 이미지 렌더러에 넣지 않는다.

`Artifact`의 제안 필드는 `artifactId`, `messageId`, `hostId`, `workspaceId`, `mime`, `revision`, `contentHash`, `displayName`, `sourceRef`다. 원본은 실행 호스트에 있고 클라이언트에는 인증된 media 참조를 준다. 썸네일과 전체 파일의 수명·용량은 구분한다.

같은 `chart.png`가 다시 생성되었을 때 과거 답변의 그림이 몰래 바뀌면 안 된다. 캐시의 키는 파일 경로 하나로 정하지 않는다. 원본 삭제·호스트 오프라인·로딩 실패에는 이유와 재시도·최신 파일 열기를 표시한다. 임시 이미지의 캐시는 줄일 수 있어도 대화에서 결과가 있었다는 기록은 남긴다.

Paseo의 유사 경로는 [Markdown images](https://github.com/getpaseo/paseo/blob/1fff127f45b11c1c9c573fbbd12791673004c912/packages/app/src/components/markdown/images.ts), [이미지 획득](https://github.com/getpaseo/paseo/blob/1fff127f45b11c1c9c573fbbd12791673004c912/packages/app/src/assistant-image/file-acquisition.ts), [캐시](https://github.com/getpaseo/paseo/blob/1fff127f45b11c1c9c573fbbd12791673004c912/packages/app/src/assistant-image/acquisition-cache.ts)에 있다. 그 캐시를 영구 문서 버전 보존 기능으로 간주하지 않고 Workbench의 revision 계약과 결합한다.

## 읽기·복사·검색이 렌더 최적화 때문에 깨지지 않게 한다

Paseo는 공통 Markdown renderer, 변경 없는 과거 행의 재사용, 스트림 묶기와 화면에 보여주는 속도를 나누는 구조를 갖는다. 이 구조를 참고하되 60ms·150ms 같은 값을 우리 앱의 검증 없이 그대로 채택하지 않는다. [스트림 설계](https://github.com/getpaseo/paseo/blob/1fff127f45b11c1c9c573fbbd12791673004c912/docs/agent-stream-performance.md), [읽기 위치 보정](https://github.com/getpaseo/paseo/blob/1fff127f45b11c1c9c573fbbd12791673004c912/packages/app/src/agent-stream/reading-anchor.ts).

다음 동작을 하나의 계약으로 검증한다.

- 오래된 질문을 펼치거나 이전 기록을 로드해도 읽던 문장이 화면에 남는다.
- 이미지가 뒤늦게 디코딩되거나 코드 블록 높이가 바뀌어도 위치가 크게 튀지 않는다.
- 완료된 응답은 남은 표시 대기 없이 전부 보인다. 부드러운 표시를 위해 최종 답변을 계속 지연시키지 않는다.
- 한글 조합 문자·이모지를 중간에서 자르지 않는다.
- 본문 일부 복사, 코드만 복사, Markdown 원문 복사를 구분한다.
- 가상화로 DOM에서 사라진 메시지도 검색되며, 결과를 누르면 그 메시지를 로드하고 정확한 위치로 이동한다.
- 접기는 화면 상태다. 원문 프롬프트·도구 결과·출처를 검색 DB에서 삭제하는 동작이 아니다.

Workbench의 이미 구현된 tool grouping과 읽기 rail을 재사용한다. 일반 `turns.map`을 가상화로 바꾸기 전에 한글 긴 대화·이미지·승인·문서 카드가 섞인 기준 fixture로 먼저 측정한다. 탭을 unmount해서 메모리를 줄이는 변경은 문서 AI 수명 분리보다 먼저 넣지 않는다.

## 하위 작업과 승인 요청을 대화에 연결한다

메인 대화에는 자식 작업의 제목·실행 기기·공급자·현재 상태·마지막 결과를 요약한다. 클릭하면 해당 문서 AI 또는 자식 대화로 이동한다. 자식 기록을 부모 답변 본문에 전부 이어 붙이지 않는다.

공급자 내부 자식은 사용할 수 있는 제어가 다르다. 읽기만 가능한 기록에 “메시지 보내기”나 “중단”을 표시하지 않는다. 승인 요청은 단순히 읽었다고 사라지지 않고, 실제 응답 결과가 확인됐을 때 해결 상태로 바뀐다. 두 기기에서 같은 승인에 응답하면 한 결과만 반영한다.

계획·선택형 질문·파일 편집 승인은 서로 다른 입력 형태다. 현재 boolean 승인만 확장해서 모든 종류를 표현하지 않는다. 특히 Codex의 지원하지 않는 질문 이벤트를 발견한 경우 해당 capability와 새 카드·응답 경로를 함께 구현한다.

## 모바일은 좁은 데스크톱 화면 이상의 검증이 필요하다

공식 iPhone 이미지는 한 열 대화와 하단 작성창을, iPad 이미지는 상태별 탐색·대화·변경사항의 분할을 보여준다. 이 화면 구조를 참고하되 HIG 계획의 토큰·접근성 기준을 유지한다. 실제 기기에서 키보드 높이, safe area, 한글 IME, 텍스트 선택, 회전, 파일 선택, 앱 복귀를 검증한다.

Paseo의 현재 소스에도 native Find·outline 미제공, 수식·동영상 비활성, SVG 대체 텍스트와 Mermaid 선택 범위 같은 제한이 있다. 모든 데스크톱 기능이 모바일에 동일하다고 간주하지 않는다. 일반 파일 첨부가 전부 인라인 미리보기되는 것도 아니다. Workbench에서는 MIME별 `대화 미리보기`, `편집 탭`, `다운로드`, `외부 앱` 지원을 명시한다.

공식 이미지 경로와 제작 조건은 [근거 문서](06-evidence.md)에 기록했다. 이미지에서 직접 확인하지 않은 인라인 이미지 기능은 소스로 확인했다.

## 구현 시작 때 수집할 성능 기준

이번에는 성능을 측정하지 않았다. 다음은 구현 전후 동일 조건으로 수집할 지표다.

| 지표 | 목적 |
|---|---|
| 첫 입력 표시·첫 토큰·최종 답변 표시 시간 | 모델 지연과 UI 지연 구분 |
| 표시 갱신 간격 p95·긴 프레임·입력 지연 | 부드러운 출력과 실제 멈춤 구분 |
| 과거 기록 양에 따른 활성 메시지 처리 비용 | 대화가 길어질수록 새 답변 처리가 무거워지는지 확인 |
| 읽던 위치 변위 | 접기·이미지 로딩·과거 페이지 추가 후 읽기 유지 |
| 이미지 첫 썸네일·전체 표시·캐시 메모리 | 품질·대역폭·용량의 균형 |
| 재접속의 캐시 표시와 최신 상태 도달 시간 | 빨리 보이는 것과 최신 상태인 것을 구분 |

기준과 변경판에 같은 기록·같은 토큰 배치·같은 이미지·같은 장치를 사용한다. 초기 실행과 재실행을 나누고 순서를 교차한다. 측정 전 임의의 속도 개선율이나 설치 용량 절감률을 목표 달성 수치로 쓰지 않는다.
