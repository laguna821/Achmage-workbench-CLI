# 이음오피스(IeumOffice) 도입 조사: Workbench에 무엇을 어떻게 가져오나

- 조사일: 2026-10-28
- 기준
  - 이음오피스: `pblsketch/openoffice` `9052297`(v0.12.7 이후), Apache-2.0, GenOffice 기반
  - Achmage HOP: 로컬 `public-1.1.0` `429b38d`(공개 최신은 1.2.0-beta.6 `d533eb4`), MIT
  - Workbench: `00fff9f`
- 앞선 기록: `office-comparison-research` R(이음·HOP·Artcraft 비교, 2026-10-22, 연구실 PC). 결론은 "통합 작업대는 이음, 한국어 양식·조판은 HOP"였다.
- 방법: 소스 읽기(하위 조사 5갈래)와 이 노트북에서 `ieumoffice` 명령줄 도구 실행 시험

## 한 줄 결론
이음의 **편집 화면은 가져오지 않는다.** 이음의 **명령줄 도구(`ieumoffice`)를 문서 엔진으로 붙이고**, 온보딩·멘션·스킬 설정은 **이음의 검증된 규칙을 Workbench 구조 위에 다시 만든다.** 한글은 kordoc(현재 승인 기본)과 HOP(목표)으로 간다.

## 이음 기능별 판단

### 1. 구독 자동 감지 온보딩
- **이음이 하는 일**
  - 첫 실행 때 설치된 `claude`·`codex`를 찾아 `--version`과 각자의 로그인 상태 명령으로 확인한다.
  - 구독과 종량제(API 키·Bedrock 등)를 구분한다.
  - 엔진을 띄울 때 과금 경로를 바꾸는 환경변수 16개를 지운다.
  - 토큰 파일은 읽지 않는다.
  - 설치 버튼은 Windows만 있다. 리눅스·맥은 공식 설치 안내 링크다.
- **Workbench의 빈틈**
  - 환경변수를 지우지 않는다(`ANTHROPIC_API_KEY`가 있으면 조용히 종량 과금으로 넘어갈 수 있다).
  - 구독/종량제를 구분하지 않는다.
  - 찾는 경로가 좁다.
  - 첫 실행 안내가 없다.
- **가져올 것**
  - `subscription/env.ts`(복사), 상태 판별기(`parseClaudeAuthStatus`·`parseCodexLoginStatus`·`codexAccountInfo`·`mergeLogins`, 수정해 사용), POSIX 경로 목록
  - 화면은 Workbench에 맞게 새로 만든다(환영 → 엔진 연결 → 문서 도구 → 완료).

### 2. MCP·스킬 연동 설정
- **이음이 하는 일**
  - 이음 안의 엔진은 사용자의 MCP를 끄고, 스킬은 자체 저장소(`~/.ieumoffice/skills`)로 관리한다.
  - 바깥 에이전트에게는 `ieumoffice mcp install`·`skill install`로 자기 MCP와 스킬을 넣어 준다.
  - "한림대 PPT 테마 적용"은 템플릿 기능이 아니었다. Achmage OS의 `hallym-ppt-system` 스킬을 사용자 스킬로 읽어 AI가 스타일로 쓴 것이다.
- **Workbench는 반대로 간다.** Workbench 엔진은 터미널에서 쓰는 Claude Code·Codex와 같은 설정을 쓴다. 그래서 별도 저장소를 두지 않는다.
  - 두 엔진의 **실제 설정**(MCP 서버, 스킬)을 한 표로 보여 준다.
  - 쓰기는 누를 때만, 쓸 경로를 보여 준 뒤, 공식 명령(`claude mcp add-json`, Codex app-server 설정 쓰기, 스킬 폴더 복사)으로 한다.
  - 프리셋: 이음 스킬(`ieumoffice` 사용설명서), Achmage MCP, hallym-kordoc.

### 3. 다양한 문서 형식
- **이음 편집기 9종(워드·엑셀·PPT·PDF·한글·마크다운·HTML·마인드맵·EPUB)을 iframe으로 넣는 건 맞지 않다.**
  - 각자 Electron 전용 기능과 수십~수백 개의 내부 통신에 묶여 있다.
  - 편집기마다 자체 AI 패널이 들어 있어 "편집기 안 AI 없음" 결정과도 충돌한다.
- **대신 `ieumoffice` 명령줄 도구를 엔진으로 쓴다.** 앱 안 `resources/cli`에 들어 있다.
  - 이 노트북 시험 결과:
    - md→docx 변환, docx→md 되읽기 정상
    - docx→PDF와 쪽 PNG 렌더링 각 약 2.6초(숨은 Electron 사용)
    - csv→xlsx 변환과 표 읽기 정상
    - 한글 글자 정상 출력
  - Workbench에서 쓰는 방식:
    - 문서 미리보기: 쪽 PNG
    - 글 보기: md·표
    - 엔진 편집: `docs/slides/sheet apply`로 작업 사본을 고치고, Workbench 수정안으로 받는다
    - 검사: `check`/`audit`
- **설치**: Linux AppImage를 받아 배포 SHA-512로 확인한 뒤, 실행 없이 풀어서 `~/.local/opt/ieumoffice/<판>`에 둔다.

### 4. 탭 문서 멘션과 형식 바꾸기
- **이음의 실제 구조**
  - "+"나 `@`로 다른 탭의 *저장된 파일*을 읽기 자료로 붙인다.
  - 지금 탭의 AI가 *자기 문서*에 쓴다. 다른 탭에 직접 쓰지 않는다.
  - 마크다운→한글 변환기는 없다. AI가 읽고 문단·표를 써 넣는다.
- **Workbench는 이미 더 단단한 계약을 갖고 있다.** 판 고정 참조(DocRef), 작업 사본, 수정안이다. 여기에 세 가지를 더한다.
  1. **`@` 멘션과 "+" 고르기**: 이음의 한글 입력기(IME) 처리 규칙을 옮긴다. 열린 문서를 먼저 보여 준다.
  2. **역할 고르기**: 붙인 문서마다 "읽기 / 고치기"를 고르고, 결과 대상으로 "새 문서: 한글·워드·PPT·엑셀·마크다운·디자인"을 고른다.
  3. **새 문서 수정안**: 엔진이 예약된 사본 경로에 새 문서를 쓰고, 적용할 때 작업 폴더에 만든다(이미 있으면 거부). 어느 문서·판에서 만들었는지(`derivedFrom`)도 남긴다.
- **열린 문서 탭**: 작업 안에서 연 문서를 탭으로 둔다. 분할 화면은 만들지 않는다.

### 5. 한글: HOP 대 이음
| | Achmage HOP | 이음오피스 |
|---|---|---|
| 글꼴 | 설치 글꼴을 직접 찾아 엔진에 공급, 한컴 글꼴 이름·HY/휴먼 처리, 대체 글꼴 정책 | 없음(upstream 기본 대체표만) |
| 축소 선명도 | 쪽 캔버스를 픽셀 격자에 맞춤(WebView2 90%에서 번짐 22%↓) | 없음 |
| 엔진 수정 | 12개: 새로 쓰거나 고친 문단을 한글 2024 출력에 맞춤 | 20개: 한컴 저장 문서의 쪽 나눔·각주·머리말·표·저장 |
| AI 편집 | 노드 ID, 사본 예행, 지문 확인, 저장 후 재열기 검증 | 38개 도구(문단·표·스타일·각주·차례…), 거래 단위 되돌리기 |
| 바깥 연결 | 앱 실행, 마크다운→HWPX 생성 워커 | `ieumoffice hwp read/apply`, `create --type hwpx`, MCP |

- 두 수정 묶음은 서로 보완한다.
- 탭 폭 처리는 서로 반대 주장이라 한컴 2024로 확인하기 전에는 섞지 않는다.

**Workbench 방침**
- 생성·미리보기는 kordoc(승인된 기본)이 맡는다.
- 사람 편집은 **HOP**이 맡는다. 1단계는 "HOP로 열기"이고, 저장하면 새 판으로 받는다.
- 내장 한글 편집기는 2단계다. HOP의 패치 엔진과 글꼴 공급·선명도 보정·저장 검증을 가져와 rhwp-studio를 `/hwp/`에 빌드한다. HOP의 Tauri 번들은 iframe으로 쓰지 않는다.
- 이음의 한글 쪽은 나중에 엔진 수정 일부만 검토한다.

## 도입 순서
1. 엔진 과금 경로 보호(환경변수 정리)와 구독/종량제 판별
2. `ieumoffice` 엔진: 감지·설치·워드/PPT/엑셀 문서(미리보기, 글 보기, 엔진 편집 안내, 수정안 전후 그림)
3. `@` 멘션, 역할 고르기, 새 문서 수정안, 열린 문서 탭
4. 첫 실행 온보딩(엔진·문서 도구)
5. MCP·스킬 설정 화면
6. HOP 연동 1단계(HOP로 열기 → 판 받기). 내장 HOP급 한글 편집기는 별도 계획으로 진행한다.
