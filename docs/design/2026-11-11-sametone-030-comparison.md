# SameTone 시기의 0.3.0과 현재 버전: 디자인·가독성·UX/UI 정밀 비교

2026-11-11 · 비교 및 개선안 · 제품 코드·설치본 변경 없음

## 결론

**이전 디자인에서 사라진 것은 글꼴 하나가 아니라, 읽기와 조작을 구분하던 시각 체계다.** SameTone의 글자 형태, 남색 제목과 강조, 중립적인 탐색 면, 실제 이름에 주던 공간이 함께 작용했다. 현재는 서체와 색을 단순화하면서 이 역할 차이까지 줄였고, 기존 조판 규칙 일부가 남아 충돌한다. 따라서 글자를 1px 키우는 조정만으로 이전의 정돈된 인상을 회복하기 어렵다.

다만 **모든 가독성이 후퇴한 것은 아니다.** 같은 내용의 네이티브 화면에서는 현재 Pretendard 본문, 숫자, 굵은 구절이 더 또렷하게 보인다. 현재의 좁은 기본 탐색기, 명확한 활성 탭, 프로젝트 안의 통합 만들기, 접을 수 있는 도구 기록도 장점이다. 되살릴 대상은 0.3.0의 읽기 위계와 정보 배분이다. 제품 전체를 되돌릴 근거는 없다.

## 1. 비교 기준과 방법

- 사용자가 말한 “0.30”의 공식 릴리즈 태그는 [v0.3.0](https://github.com/laguna821/Achmage-workbench-CLI/releases/tag/v0.3.0)이다.
- 당시 소스: `7b174e5b2aa4fbe29e95a8f47c8e1f62a17c91b5`. 현재: `b417433dfc58929d354aa779c600d071b91bdfd8`, 설치된 0.4.1 기반 로컬 수정본.
- 공식 0.3.0 Linux 패키지의 해시를 릴리즈 값과 대조한 뒤, 설치하지 않고 별도 테스트 프로필에서 실행했다. 현재 설치 바이너리도 별도 프로필에서 실행했다.
- 같은 프로젝트명, 세션명, 문서와 테스트 응답을 사용해 **홈·프로젝트·대화 라이트·대화 다크 4쌍**을 캡처했다. 모델 호출이나 사용자 대화·DB 사용은 없었다.
- 같은 HTML 구조를 각 버전의 실제 대화 CSS로 표시해 H3/H4/강조 역할을 비교했다. 이 두 장은 내용 주입을 명시한 **의미 위계 표본**이다.
- 서체 자체 비교는 17px / 400 / 행간 1.6 / 자간 0 / 동일 색상으로 분리했다. 큰 제목은 28px / 600, 작은 표본은 13px이다.
- 환경은 동일 Linux WebKitGTK, 격리 X11, 1440×1000, DPR 1이다. 실제 노트북 125% 합성과 Windows/macOS에서의 차이는 이번 결과로 확정하지 않는다.
- Impeccable typeset·기술 감사 및 Hallmark 기존 앱 재설계 관점으로 독립적인 서체/소스 검토와 시각/UX 검토를 수행했다. 자동 엔진 점수나 사용성 실험 결과로 포장하지 않는다.

이전 R16이 사용한 0.3.3과 이번 0.3.0 사이에는 비교 대상 `styles.css`, `appearance.ts`, `navigator.css`, `panes.css`, 번들 글꼴의 차이가 없다. 이전 수치는 유효하지만, 당시 분석 범위는 이번 요청보다 좁았다.

## 2. SameTone과 Pretendard의 차이

### 실제로 쓰인 위치

| 역할 | 0.3.0 | 현재 기본 |
|---|---|---|
| 사이드바·메뉴·탭·일반 UI | Pretendard 우선. 없으면 한글 영역에 SameTone Hangul 폴백 | 번들 Pretendard |
| 상단 제목·쪽 제목·프로젝트 섹션 제목 | SameTone 계열 display 역할 | Pretendard |
| 대화 본문·사용자 요청·입력창 | 엔진 기본 SameTone | 엔진 기본 Pretendard |
| 프로젝트의 큰 제목 | UI 서체 상속 | Pretendard |
| 코드·명령 | 별도 고정폭 서체 | 별도 고정폭 서체 유지 |

**“SameTone 시기”와 “화면의 모든 글자가 SameTone”은 다르다.** 특히 사이드바의 문제를 전부 서체 교체 탓으로 설명하면 잘못된 처방이 된다.

### 같은 px로 맞춰도 다른 이유

실제 번들 글꼴을 fontTools로 읽어 wght=400에서 비교했다. 두 글꼴 모두 UPM은 2048이다.

| 항목 | SameTone | Pretendard | 의미 |
|---|---:|---:|---|
| hhea ascender / descender | 2200 / −600 | 1950 / −494 | 같은 CSS 크기라도 글꼴 내부 세로 메트릭이 다름 |
| x-height / cap-height | 1050 / 1448 | 1086 / 1448 | 영문 소문자의 상대적 크기가 다름 |
| 한·글·가·나·다 각각 advance | 0.86426em | 0.86426em | 글자 진행 폭은 같음 |
| I / l advance | 0.33887 / 0.28613em | 0.24414 / 0.21777em | 영문 좁은 글자의 폭과 형태가 다름 |
| 0 / 1 advance | 0.60693 / 0.60693em | 0.59570 / 0.43848em | 기본 숫자 폭의 성격이 다름 |

한글 폭이 같아도 자형은 같지 않다. 예를 들어 ‘나’의 왼쪽 윤곽 경계는 0.05078em과 0.07129em으로 다르고, ‘한’·‘나’의 윤곽 그리기 명령 수도 다르다. 문서의 “Pretendard 유래” 설명은 출처 설명이지 두 파일의 획이 동일하다는 뜻이 아니다.

실제 같은 크기 표본에서도 SameTone은 획의 대비와 끝맺음, 세리프 영문 때문에 문서 편집물에 가까운 인상이 강하다. Pretendard는 획이 균일하고 작은 영문·숫자가 더 안정적이다. **SameTone의 개성은 px 조절로 재현할 수 없지만, 시각적 위계는 Pretendard로도 만들 수 있다.**

이 수치와 관찰은 자형 차이를 설명한다. 과거 사용 당시의 안티앨리어싱 품질, 장시간 읽기 속도 또는 어느 글꼴의 객관적 우월성을 입증하지 않는다.

## 3. 읽기 디자인: 실제로 약해진 부분

### 강조가 일반 문장처럼 보이는 문제

기존 CSS는 한글을 기울이지 않기 위해 `em`을 normal 스타일로 두고 **색으로 강조**했다. 현재 기본 팔레트는 그 강조색도 본문색과 같게 만들었다.

| 같은 의미 표본 | 0.3.0 Codex 라이트 | 현재 Codex 라이트 |
|---|---|---|
| 본문 | 16px / 400, `#0e1726` | 17px / 400, 검정 |
| `em` 강조 | 16px / 400, `#00328d` | **17px / 400, 본문과 같은 검정** |
| `strong` 강조 | 16px / 600, `#002870` | 17px / 600, 검정 |
| H3 | 18px / 600, 남색 | **17px / 600, 검정** |
| H4 | 16px / 600, 다른 남색 | **17px / 600, 검정** |

현재 `em`은 주변 문장과 거의 구분되지 않고, H3와 H4는 크기·굵기·색·행간·여백까지 같아졌다. 이는 취향보다 먼저 해결할 **의미 전달 문제**다. H2는 오히려 20→22px로 커졌다. “제목을 전부 작게 만들었다”가 아니라 **중간·하위 위계가 무너졌다**가 정확하다.

### 문단 리듬과 읽기 폭

- 0.3.0 Codex 본문은 16px / 행간 27.2px, 현재는 17px / 29.75px다.
- 문단 간격은 기존 0.75em에서 현재 16px로 바뀌었다. 현재는 더 여유롭지만 한 화면의 정보량은 줄어든다.
- 실제 일반 대화 본문 폭은 **712→720px**다. 읽기 폭 자체가 크게 줄어든 것은 아니다.
- 조밀한 분할 패널에서는 현재 CSS가 다시 15px / 1.6을 강제한다. 이는 소스에서 확인한 별도 문제이며 이번 화면은 일반 패널이다. 여러 패널을 열 때 사용자 서체 설정이 어떻게 반영되는지 명확히 해야 한다.

### 시선이 머무는 지점

0.3.0에서는 남색 제목·강조, 별도 색상의 코드 블록, 인용과 표의 규칙이 읽기 위치를 잡아줬다. 현재는 본문·표·제목이 같은 흑백 계열로 통일되어 안정적인 대신 평평하다. 색을 많이 되돌릴 필요는 없지만, 제목·강조·메타·코드의 역할 차이는 다시 확보해야 한다.

| 현재 위치 | 이전에는 접힌 프로젝트가 내부 활성 세션의 위치를 대신 표시. 현재는 이 단서가 빠짐 | 선택 상태와 별개로 ‘현재 작업 포함’ 단서를 제공 |

181→125px는 이 테스트의 동일 세션명·동일 창에서 얻은 **행 제목 영역 실측**이다. 약 31% 감소이며 모든 목록의 보편 수치로 일반화하지 않는다. 새 트리의 들여쓰기와 반복 표시가 원인에 포함된다.

## 5. UX: 단순해진 것과 찾기 어려워진 것

| 사용 상황 | 0.3.0 | 현재 | 권장 |

| 처음 작업 시작 | 엔진 선택·입력·작업 개요가 함께 보임 | Search/Ask와 입력이 중심 | 현재의 단순한 시작 유지 |

현재 공통 메뉴는 키보드 이동·닫은 뒤 포커스 복귀·체크 상태·비활성 설명이 개선됐다. 이런 상호작용 성과는 유지해야 한다.

**웹 탭 비교의 경계:** 공식 0.3.0에는 현재의 공유 브라우저 화면 `BrowserView.tsx`가 없다. 따라서 현재 NAVER 웹 탭을 0.3의 같은 화면에 대한 단순 리스킨으로 비교할 수 없다. 여기서는 두 버전에 공통인 대화·프로젝트·홈을 비교했다.

## 6. Impeccable·Hallmark 관점의 판단

- **Impeccable: 역할과 위계.** 폰트 이름·크기를 바꾸는 것보다 제목, 본문, 강조, 메타의 관계가 중요하다. 이번에는 기존 역할을 제거한 뒤 대체 수단을 충분히 마련하지 못했다.
- **Impeccable: 실제 서체에 맞춘 조판.** SameTone의 세리프·획 대비와 Pretendard의 균일한 획은 다른 리듬을 요구한다. 같은 400·600 숫자를 썼다고 같은 시각적 효과가 되지 않는다.
- **Hallmark: 앱의 정보 배분.** 종류를 친절하게 설명하려고 반복한 문구가 중요한 작업명을 밀어낸다. 이름·현재 위치·다음 행동이 먼저 읽혀야 한다.
- **Hallmark: 절제와 개성의 균형.** 시각적 정리는 장식을 없애는 것만으로 끝나지 않는다. 기존의 특징을 줄였다면 여백·면·위계의 완성도로 이를 대체해야 한다.
- **마이그레이션 관점.** 현재 `em`의 소실과 H3/H4 동일화는 기존 조판 CSS와 새 색상·크기 덮어쓰기의 충돌이다. HIG 자체의 한계로 볼 이유가 없다.

## 7. 개선안: 복원·유지·재설계

### 먼저 복원할 것

1. **강조와 하위 제목의 의미.** H2/H3/H4를 다시 구분하고 `em`이 일반 문장과 보이게 다르게 만든다. 색 하나만 의존하지 않도록 크기·굵기·여백을 함께 설계한다.
2. **이름 중심 탐색.** 묶음 안의 반복 ‘채팅/문서 AI/웹 AI’를 줄인다. 혼합 검색·탭처럼 구분이 필요한 곳에서는 아이콘·종류 정보를 유지한다.
3. **조용하지만 충분한 대비.** 작업명·비활성 탭 이름을 보조 글자와 분리한다. 예전의 중립 탐색 면과 읽기 면 구분을 현대적인 형태로 복원한다.
4. **재개할 때 필요한 맥락.** 홈과 프로젝트에 최근 결과·확인 필요·현재 작업 위치를 짧게 제공한다.

### 유지할 것

Pretendard 기본, 현재의 단일 프로젝트 트리 기본값, 명확한 활성 탭, Search/Ask 진입, 프로젝트별 만들기, 웹·문서의 독립 AI 대화, 메뉴 키보드 동작, 도구 기록 접기, 현재 본문의 숫자·목록 가독성.

### 다시 설계할 것

서체 역할·간격·색상 토큰을 한 곳에서 관리하고 기존 고정값 덮어쓰기를 정리한다. 탐색 색상은 선택한 에이전트의 외형으로부터 독립시킨다. 조밀한 분할 화면은 보조 정보를 먼저 줄이고 핵심 이름과 사용자 읽기 설정을 우선한다. 빈 속성은 기본 개요를 압도하지 않게 한다.

**서체에 대한 제안:** 현재 승인된 기본 Pretendard는 유지한다. SameTone의 문서 같은 인상은 필요하면 기존 읽기 서체 선택에서 별도로 비교할 수 있지만, 서체만 되돌려도 중복 라벨·강조 소실·폭 배분 문제는 남는다. 사이드바 전체를 SameTone으로 바꾸는 것도 0.3.0의 역할 구조를 복원하는 방법이 아니다.

## 8. 완료 기준과 범위

다음 구현의 완료 기준은 px 수치나 스타일 검사 통과가 아니다.

- 긴 한글 작업명과 현재 프로젝트가 쉽게 식별된다.
- 제목 단계, 일반 본문, 강조 문구가 내용 없이도 구분된다.
- 단순한 홈에서 돌아온 작업의 최근 상황을 알 수 있다.
- 현재 메뉴와 독립 문서·웹 작업의 사용성이 유지된다.
- 실제 노트북 125% 배율에서 같은 영역을 확인하고, 다른 OS의 렌더링 결과를 이 Linux 결과로 대신하지 않는다.

이번 작업은 비교·원인 분석·개선 우선순위까지다. 새 빌드, 설치 교체, 기본 서체 변경은 수행하지 않았다.
