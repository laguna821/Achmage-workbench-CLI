# 구현 순서와 종료 조건

계획의 대상은 [화면 목록](screen-inventory.md) S01~S15다. [HIG 결정](decisions.md) D01~D14와 [정확한 연구 revision](sources-and-evidence.md#연구-기록)에 연결한다. **이번 턴에서는 계획 문서만 작성했으며 아래 구현·제품 테스트는 미실행이다.**

W6의 화면 사양은 W0부터 설계하되 실제 엔진 실증이 필요한 항목은 분리한다. **“현재 기능 전체 HIG 개편”과 “신규 Aside형 웹 기능까지 구현”의 완료 상태를 각각 보고**한다. 웹 엔진 연구가 기존 UI 개편을 무기한 막거나, UI 시안이 웹 기능 완료로 둔갑하지 않게 한다. [Engineering]

## 현재 코드에서 시작할 방법

| 코드 경계 | 관찰 | 실행 계획 |
|---|---|---|
| `App.tsx` 2,441줄 | View·전역 상태·탐색·대화상자·패널 조립이 모임 | 상태/명령은 기존 경로에 두고 새 셸 컴포넌트로 표시 역할을 분리. 먼저 전체 state를 다시 쓰지 않음 |
| `styles.css` 6,455줄 | 공통 토큰과 화면 스타일이 함께 있음 | 이관한 컴포넌트부터 scoped style로 이동, 기존 토큰 역할을 명시. 전역 선택자로 모든 편집기 DOM을 덮지 않음 |
| `appearance.ts` | 엔진별 외형·사용자 설정·이전 값 호환 | 설정 값과 사용자 선택 보존; 새 기본값 적용 범위를 명시 |
| `tabs/panes/layout-persistence` | 안정된 탭 ID·레이아웃 저장 | 새 레이아웃도 같은 작업 ID를 사용. 이전 저장 레이아웃을 읽는 호환 경로 유지 |
| `OfficeEditor.tsx` | 별도 origin iframe, 문서 토큰·저장 판·AI 메시지 | 스타일 변경으로 iframe을 재마운트하지 않음. theme/state 메시지 계약으로 적용 |
| `apps/office/vite.config.ts` | upstream renderer와 빌드 시 adapter/patch | 업스트림 원본의 광범위 수정 대신 좁은 컴포넌트/스타일 어댑터. 업데이트 시 대응 지점 확인 |
| `SearchPalette/ModelPicker/notifications` | 기존 검색·모델·알림 로직 | 화면만 재구성해 원문 검색/실제 모델 목록/완료 이벤트를 연결 |

줄 수는 복잡도 경계를 찾는 관찰값이며, 코드가 나쁘거나 전부 버려야 한다는 증거가 아니다. UI만을 위한 새 DB나 별도의 AI 세션 저장소는 만들지 않는다. [Engineering]

공통 컴포넌트는 스킬 HIG Kit의 구조·상태·접근성 동작을 기준으로 기존 React 상태와 연결한다. 기존 브랜드 토큰을 역할별로 매핑하며, 같은 메뉴를 Kit 스크립트와 React가 중복 제어하지 않도록 소유권을 하나로 정한다. 필요한 범위를 확인한 뒤 코드에 반영한다. [Engineering]

## 편집기 이관에서 지킬 경계

1. 문서 내용과 도구 UI에 다른 스타일 scope를 둔다. Word/HWP 페이지, 슬라이드, 셀, Markdown 원문을 UI 서체로 덮지 않는다.
2. 기존 명령을 새 메뉴/도구에서 호출한다. 기존 기능마다 새 위치를 기록하고 고급 명령도 찾을 수 있게 한다.
3. 편집기별 selection·undo·dirty·save revision과 독립 AI 세션을 보존한다. UI 재배치가 문서 닫기/권한 해제 이벤트가 되지 않게 한다.
4. 사용자 설정이나 테마 전환은 가능한 범위에서 상태 업데이트로 처리한다. 문서를 다시 로드해야 하는 변경은 그 필요성과 미저장 상태 처리부터 정의한다.
5. 외부 이음오피스 자체의 UI는 별도 앱의 영역이다. 이번 전면 개편은 **Workbench 안의 편집기 UI**를 포함하며, 독립 설치된 외부 앱까지 새로 포크하는 작업으로 확대하지 않는다.

## 필요한 검증만 단계적으로

- 공통 UI: 메뉴 키보드·focus trap·disabled 이유·상태 표시처럼 실제 사용자 동작을 검증한다.
- 기존 시험 재사용: `tabs`, `panes`, `layout-persistence`, `office-agent`, `document-session`, `search-preview`, `appearance`, 모델 선택 관련 시험 중 변경 경계를 우선 실행한다.
- 실제 앱: `scripts/app-e2e/usability.ts`, `navigation.ts`, `tabs.ts`, `office-conversation.ts`, 형식별 office 시나리오, `fast-find-run.ts`를 새 진입점에 맞춰 사용한다. 단위 시험 통과만으로 iframe·IME·native focus가 검증됐다고 하지 않는다.
- 시각 검토: 대표 화면은 모든 외형/확대 조건, 형식별 편집기는 주요 도구·메뉴·AI·저장 흐름을 확인한다. 같은 화면을 근거 없이 무한 재캡처하지 않는다.
- 스킬 검증: 구현 산출물에는 `find-rules.mjs --check`, 실제 미리보기에는 `audit-page.js`와 눈으로 보는 위계 검토를 적용한다. 자동 감사만으로 좋은 사용감이 확인됐다고 보지 않는다.

## 중간 전달과 최종 종료

W2에서 **실제 작동하는 대표 세 화면**을 검토 가능하게 만든다. 색만 바뀐 스크린샷을 첫 사용성 결과로 내놓지 않는다. 이후 미완료 항목은 S##·H##로 보고해 무엇이 끝났고 무엇이 남았는지 고정된 목록에서 추적한다.

전면 개편 완료는 기존 기능에 해당하는 모든 화면군과 H01~H14가 통과한 때다. 새로 떠오른 기능이나 다른 미감 후보를 완료 조건에 계속 추가하지 않는다. 해당 기준을 깨는 결함은 수정하고, 추가 요구는 별도 범위로 기록한다. 버전 숫자나 “더 예뻐질 때까지”를 종료 조건으로 삼지 않는다.
