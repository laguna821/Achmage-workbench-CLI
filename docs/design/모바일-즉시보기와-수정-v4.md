# 모바일에서 즉시 보고 수정하기 — v4

2026-10-16 · 설계 제안 · iOS/문서 렌더/편집 통합 실험 미수행

## 이번 수정의 이유

사용자의 병목은 모바일에서 파일을 확인하기 위해 이미지 재요청, Dropbox 이동, 전용 앱 설치, 대화 복귀를 반복하는 것이다. 연결만 되거나 PC 편집기를 작은 화면에 넣는 것만으로는 해결되지 않는다.

v3의 공통 work·artifact revision·실행 호스트·저장 확인 계약을 유지한다. 초기 검증을 Markdown 중심으로 두던 순서는 변경한다. 실제 HTML·PDF·한글 결과를 휴대폰에서 보고 고칠 곳을 짚는 흐름을 첫 검증 범위에 포함한다.

핵심 제품 조건: 선언된 결과물을 만들면 사용자가 모바일에서 볼 수 있는 표현과 원본에 연결된 수정 경로까지 준비한다. 파일 생성 완료와 미리보기 준비 완료를 구분하고, 준비되지 않았으면 상태를 정직하게 표시한다.

## 기본 경험

1. 대화에 파일 링크와 함께 첫 화면/페이지 미리보기가 자동 표시된다.
2. 미리보기를 누르면 현재 작업 안에서 크게 열린다. 뒤로 가면 같은 대화·스크롤 위치로 돌아간다.
3. 문장 선택 또는 영역 지정 후 현재 입력창에 “여기 더 짧게”, “이 표 다음 페이지로” 등을 입력한다. 선택 위치는 입력창에 작은 표시로 남는다.
4. 짧은 문장이나 지원되는 표 값은 선택 직후 작은 편집창에서 직접 고친다. 직접 편집을 위해 AI 호출이 필요하지 않다.
5. 수정 후 해당 부분과 새 미리보기를 보여준다. 사용자가 보고 있던 문서 위치를 최대한 유지하고, 동일 revision을 다음 Claude/Codex 작업에 전달한다.
6. 큰 레이아웃 작업은 PC에서 같은 문서·위치·미처리 요청으로 이어간다. 모바일에서 정밀 편집을 시도할 선택권도 지원 범위 안에서 남긴다.

화면은 문서/결과 면 하나와 기존 입력창을 중심으로 유지한다. 파일 종류별 앱 선택 화면을 기본 흐름에 넣지 않는다. 형식별 “직접 편집 가능/위치 연결 요청 가능” 능력은 맥락에 맞게 나타낸다.

## 형식별 처리

| 형식 | 기본 보기 | 수정 경로 | 한계와 확인 |
|---|---|---|---|
| HTML | PC 시안이면 고정된 PC viewport의 실제 렌더 미리보기, 모바일 페이지면 반응형 실제 웹 화면 | DOM/컴포넌트가 매핑된 선택 또는 영역+설명, 지원되는 텍스트 직접 편집 | 스크린샷은 클릭 동작을 증명하지 않음. 상호작용은 격리된 실제 페이지에서 별도 실행 |
| PDF | 앱 내부 PDF.js 페이지 뷰어, 무거운 문서는 서버 페이지 이미지 | 주석/영역 요청, 원본 저작 파일이 있으면 그 원본을 고친 뒤 재출력 | PDF 뷰어를 붙여도 임의 본문 편집기가 생기지 않음. 원본 없는 PDF의 수정 범위는 도구별 검증 |
| HWP/HWPX | 호스트의 선택된 검증 엔진으로 페이지 표현 생성 | 구조 위치가 확인된 문단·표 셀은 간단 편집, 복잡한 배치는 위치 연결 요청 | HWP는 읽기 입력. 최종 한글 파일은 승인된 워크플로우의 HWPX. 글꼴·표·쪽나눔 재현성 실기 필요 |
| Markdown | 모바일 폭에 맞는 읽기와 직접 편집 | 문단/블록 편집, 선택 텍스트 질문 | 링크·메타데이터 보존, 한글 조합 입력 확인 |

문서의 원본 배치와 모바일에서 읽기 편한 내용 표현은 구분한다. 작은 화면에서 글을 크게 보는 “내용 보기”는 선택 기능이다. 내용을 재배치한 화면을 원본 페이지 검수 화면으로 제시하지 않는다. PDF/한글의 내용 추출이나 OCR이 불확실하면 정확한 본문 편집으로 가장하지 않는다.

모든 형식을 하나의 새 편집 형식으로 강제 변환하지 않는다. 원본과 여러 표현을 같은 artifact에 연결한다. 사용자는 일관된 조작을 쓰고 내부에서는 형식별 기능을 적용한다.

## 모바일의 세 가지 구현 선택

- 브라우저 직접 처리: Markdown/가벼운 HTML/PDF에 적합한 기본 후보. 모바일 성능과 기능 호환성 검증 필요.
- 실행 호스트 렌더 + 가벼운 보기: 복잡한 문서와 PC 시안의 기본 후보. 폰은 필요한 이미지/텍스트/위치 정보만 받고 원본 작업은 호스트에서 수행한다. 호스트 자원과 연결이 필요하다.
- 앱 내부 원격 화면: 특수한 데스크톱 편집 기능을 꼭 써야 할 때의 후속 선택지. 작은 조작 대상, 지연, 상시 세션 자원 때문에 기본 경로로 삼지 않는다.

추천은 앞의 두 방식을 파일과 기기 상태에 맞게 조합하는 것이다. 일반 결과 확인에 원격 데스크톱 연결을 요구하지 않는다. Tailscale은 이 서비스에 접속하는 기반이며 뷰어·편집·위치 전달 기능 자체는 앱이 구현한다.

## 산출물과 위치 계약

필수 데이터는 artifactId, sourceRevision/hash, 원본 위치, mediaType, 생성에 사용한 renderer/version, previewRevision, viewport/페이지 크기, 준비 상태, 편집 지원 범위다. 표현별 파일은 서버가 관리하며 모든 원본 경로를 브라우저에 직접 공개할 필요는 없다.

수정 요청은 원본 판, 페이지/화면, 선택 영역의 정규화 좌표, 선택 텍스트, 가능한 구조 노드 ID, 사용자 지시를 함께 담는다. HTML의 DOM ID, Markdown의 블록, HWPX의 문단/셀, PDF 텍스트 위치는 각 어댑터가 대응시킨다.

이미지 위에 그린 영역은 위치 단서다. 그것만으로 모든 원본 구조를 정확히 찾을 수 있다고 가정하지 않는다. 구조 매핑이 없는 경우 이미지 crop과 텍스트/페이지를 AI에 전달하고 수정 제안으로 처리한다. OCR만으로 추측한 셀에 자동 덮어쓰기를 하지 않는다.

수정 시 baseRevision을 확인하고, 원본 갱신 후 해당 previewRevision을 무효화한다. 이전 미리보기를 잠시 보여줄 때는 갱신 중임을 표시하고 오래된 판에 새 요청이 묶이지 않도록 한다. 렌더 완료는 sourceRevision과 대조해 원자적으로 게시한다. 늦게 도착한 이전 판 렌더가 최신 미리보기를 덮어쓰지 않는다.

쪽수가 변하면 페이지 번호만으로 복귀하지 않고 가능한 문단/블록 anchor를 사용한다. 대응 실패 시 사용자에게 변경 위치를 보여주고 재선택을 요청한다. 사용자에게 매 요청마다 파일/페이지를 직접 설명하게 만들지는 않는다.

## 자동화와 경량화

대상이 되는 것은 AI/사용자가 선언한 결과물이다. 디렉터리의 모든 임시 파일과 키 입력마다 전체 문서를 렌더하지 않는다.

첫 화면·현재 페이지와 가까운 페이지만 우선 준비한다. 미리보기 캐시는 원본 hash + renderer/version + viewport 기준으로 재사용하고, 변경된 부분의 재렌더가 안전한 경우만 부분 갱신한다. 탭별로 무거운 편집기나 브라우저를 상시 여러 개 띄우지 않는다. 필요 시 적은 수의 렌더 작업자를 사용하고 idle 종료 정책을 둔다.

HTML 캡처는 생성 이미지가 아닌 실제 브라우저 렌더로 만든다. 일반 캡처/전달에 추가 LLM 호출은 필요 없다. OCR과 의미 기반 수정은 필요할 때만 별도 처리한다. “모델 비용 없음”이 CPU/RAM/전송 비용도 없음을 뜻하지 않는다.

새 무거운 렌더/추출을 실제 구현·실행할 때는 등록된 resourceManagement와 stable launcher 경로를 따른다. 기존 앱 프로세스를 임의 채택하거나 종료하지 않는다. 이번 설계 작업에서는 렌더를 실행하지 않았다.

생성 HTML은 앱 제어 권한과 분리된 origin/sandbox에서 실행하고 외부 자산·로그인 의존성을 감지한다. 인증된 콘텐츠 서비스로 필요한 결과만 제공한다. 폰에 공급자 토큰을 복사하지 않는다. 다운로드·공유는 사용자가 원할 때 이용하는 출력 경로이며 필수 확인 단계로 넣지 않는다.

호스트 오프라인 상태에서는 미리 캐시된 결과만 볼 수 있다. 새 렌더/AI 수정은 대기 상태로 남기며 완료로 표시하지 않는다. 오프라인 캐시 크기와 iOS 저장 지속성은 실제 기기 검증 후 정한다.

## 첫 기능 검증

실제 사용자 파일 3종으로 시작한다: PC 폭의 HTML 시안, 표와 여러 페이지가 있는 PDF, 기존 한글 문서. 문서 원본을 허가 없이 변환·수정하지 않으며 작업 사본과 생성 결과를 구분한다.

합격 기준:
1. 휴대폰에서 별도 앱 설치·DropBox 이동·이미지 재요청 없이 첫 화면을 확인한다.
2. 문장/표/영역을 선택하고 “여기 수정”만 말해도 문서와 위치가 전달된다.
3. 수정 결과가 같은 작업으로 돌아오고 변경된 위치를 확인한다.
4. 직접 편집과 AI 작업이 겹쳐도 사용자 수정은 보존한다.
5. 이전 판 미리보기·렌더 실패·OCR 불확실성을 최신 완료로 표시하지 않는다.
6. 모바일→PC→다른 제공자 세션 전환에도 문서 판과 선택 위치를 보존한다.

측정: 결과 확인까지 걸린 시간, 대화/앱 왕복 횟수, 수동 첨부/재설명 횟수, 위치를 잘못 고친 비율, 렌더 RAM, 준비 대기 시간. 최저 RAM 수치나 모든 파일 지원을 미리 약속하지 않는다.
