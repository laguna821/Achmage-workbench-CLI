# 사용자 양식과 스킬 보관함

대화창 또는 문서 채팅의 **새 문서로 만들기 → 내 양식·스킬에서 만들기**에서 보관함을 연다. 설정의 MCP·스킬 화면에서도 같은 보관함을 관리한다. 개인 문서 등록, 폴더·ZIP·GitHub 가져오기, 양식 미리보기, 사본 편집, ZIP 내보내기, GitHub 업데이트가 있다.

## 원본과 선택

- 프로젝트 스킬, 선택한 엔진의 설치 스킬, 다른 설치·공유·플러그인 스킬, 내 보관함, 이음 설치, 번들 순서로 같은 이름의 판을 선택한다. 우선 판을 꺼도 하위 판을 자동으로 켜지 않는다.
- `.codex`에서는 `skills` 하위만 읽는다. 인증 홈을 가리키는 폴더 링크와 스킬 폴더 밖으로 나가는 파일 링크는 읽지 않는다. 설치 스킬과 사용자가 등록한 원본 문서는 수정하지 않는다.
- `metadata.ieum-template`의 `assets/` 파일과 `ieum-title`을 사용한다. Workbench 사본을 만들면 다른 스킬 이름을 붙여 원래 설치 판과 구분한다.
- 가져온 스킬은 **꺼짐 / 수동 선택**이다. 같은 이름을 교체해도 다시 선택해야 한다. 이 상태는 Claude·Codex의 자체 설치 설정과 별개다. 일반 CLI 채팅의 직접 연결은 선택한 양식 설명이며, 원본 Office9종에서는 아래의 여러 스킬 선택과 읽기를 지원한다. 자동 호출의 별도 인수는 후속이다.
- 교체·삭제한 보관함 사본은 gateway 데이터의 `skill-backups/`에 남긴다. ZIP에는 양식도 포함하고 GitHub 설치 추적 파일은 제외한다. GitHub 업데이트는 변경 파일과 로컬 수정 여부를 먼저 보이며, 로컬 수정을 교체하려면 명시적으로 선택해야 한다.

## 한 번만 만드는 새 문서

미리보기는 양식 파일과 스킬 설명 각각의 SHA-256을 확정한다. 요청 전에 원본이 바뀌면 다시 선택하도록 하고, 옛 미리보기를 새로운 양식으로 조용히 바꾸지 않는다. 양식 파일은 `template-snapshots/`, 설명은 `template-instructions/`에 내용 해시로 보관한다.

호스트는 작업공간에 새 파일을 독점 생성한다. 양식은 사본으로, 빈 새 문서는 빈 예약 파일로 시작한다. 같은 이름이 있으면 번호를 붙인다. `document-creation:*` 기록에 요청 ID, 세션·작업공간, 파일 경로, 원본 해시, 상태와 결과 문서를 보관한다. 서로 다른 세션의 동시 요청도 같은 이름을 예약하지 않는다.

같은 요청 ID의 동시 호출은 엔진에 한 번만 전달한다. 같은 ID로 다른 내용을 보내면 거절한다. 준비 과정만 직렬화하고 엔진 실행 뒤에는 기존 끼어들기·대기 요청을 사용할 수 있다. 앱을 다시 시작하면 중단된 사본과 안내를 복구하며, 실행 여부가 불확실한 엔진 요청을 자동으로 다시 보내지 않는다. 전용 재개 버튼은 아직 없고 복구한 문서를 열어 후속 요청으로 이어간다.

완성한 결과는 요청한 창에 내부 문서 탭 하나로 연다. 원래 대화는 유지한다. 다른 탭에서 작업 중이면 배경 탭으로 추가하며, 시작 탭을 이미 닫았거나 다른 창에서 이벤트를 받았다고 화면을 전환하지 않는다. 요청 기록과 Markdown 내보내기에 선택한 양식의 이름·파일 해시·설명 해시가 남는다.

## 원본 Office 대화에서 사용

9개 원본 편집기의 입력창에서 `/` 또는 `$`로 여러 스킬을 선택한다. 표시되는 칩과 본문 판은 같은 Workbench 대화에 남고, 스킬 안의 텍스트 자료는 원본 `read_skill_file` 도구로 읽는다. 설치 스킬의 스크립트는 실행하지 않는다. 관리 메뉴는 위의 보관함을 연다.

선택한 스킬에 양식이 있으면 원본을 보존한 사본을 같은 작업공간의 새 내부 탭으로 열고, 같은 대화에 모든 선택 스킬과 요청을 한 번 인계한다. 같은 대화에서 후속 요청을 보내거나 사본을 직접 편집할 수 있다. 재열기 후에는 사용했던 스킬의 현재 본문을 다시 읽는다. 스킬이 꺼지거나 판이 바뀐 채 전송되면 조용히 다른 판으로 대체하지 않는다.

이 경로의 Linux 실제 앱 검사는 **86/86**, 관련 회귀는 **84/84**다. PPT에서 Word 양식으로 이동·직접 편집·저장·같은 대화의 AI 입력까지 확인했다. 제안 카드의 저장과 현재 문서를 양식으로 미리 보는 원본 경로는 아직 연결 중이다. 검증 판 `research:rr-23b6877f1f5f065e3f98bd3a61ee42a4:b55ba6f1df5fb74aeef5bf9d69cae5a628ffaf0fac302c488c9168d0f6876646`; 상세 범위는 [Office 통합](office-integration.md)에 기록한다.

## 근거와 검증 범위

이음의 Node-only user-skills/zip-gate 코어 18개 파일은 고정 판 `30ff4f051f067fcb2baf1ab416c40718c802ca35`에서 분리했다. `third_party/ieumoffice/user-skills.manifest.json`에 원본·적용본 해시를 기록하며 `node scripts/vendor-user-skills.mjs --check`가 빌드 전 일치 여부를 확인한다. `--write`는 고정 판과 출처를 의도적으로 갱신할 때만 사용한다.

호스트 회귀는 설치 우선순위, 원본·외부 경로 보호, 사본 편집 CAS, ZIP 경계, GitHub 변경·로컬 수정·백업, 동시 생성과 재시작 중복 방지를 검사한다. 실제 Linux Tauri/WebKitGTK 전체 흐름 **68/68**이 통과했다. 개인 Markdown 등록부터 미리보기·같은 세션 생성·중복 요청·결과 새 탭·재열기를 포함한다. 엔진은 대역이며 실제 모델 생성 품질 검증은 아니다. 생산 의존성 감사는 취약점 0개였다.

추가 PPTX native **12/12**이 통과했다. synthetic 양식의 실제 페이지 렌더링, 동일 바이트 사본, Slides의 실제 입력·저장·재열기, 미수정 테마·마스터·레이아웃 보존, 같은 세션의 후속 판·해시 참조를 검증했다. 기존 Electron 페이지 렌더에는 하네스 전용 Xvfb가 필요하며 이 의존성 제거는 남아 있다.

실제 Codex gpt-6.1-sol / medium 검사도 **16/16** 통과했다. 사람이 저장한 PPTX를 같은 세션에서 검토하고 Markdown 지시를 읽어 수정안을 만든 뒤 UI로 적용했다. 정확한 제목 변경, 같은 내부 편집기 갱신과 원본·참조·미수정 테마/마스터/레이아웃 보존을 확인했다.
